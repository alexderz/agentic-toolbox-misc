### 1. StrataFlux: a low-bit engine that borrows precision from RAM and SSD (research)

- **What it is:** a framework paper, [StrataFlux: Memory-Hierarchy-Native Low-Bit LLM Inference](https://arxiv.org/abs/2611.08363),
  for running 2-4-bit weights and 2-3-bit KV caches while keeping the higher-precision "refinement" bits in host RAM or
  on an SSD and fetching only the parts each token needs. From the [post](https://x.com/swarogan/status/2124102691194306800).
- **What we checked:** the arXiv record and abstract (title, id and every number below are from it), a GitHub and web
  search for a code release, and the licence (none to read: no repository found, the paper links none). Iris's summary
  matches the abstract.
  - Authors' headline results: Llama-3.1-8B at 2-bit weights drops WikiText-2 perplexity from 9.46 (plain 2-bit) to
    8.40 at 95.4% of the quantized base's throughput on a 5090. Qwen3-8B at 2-bit weights and KV goes from 11.0% to
    47.1% on AIME 2024/2025 at the same GPU memory. Llama-3.1-8B at 128K with 3-bit weights and 2-bit KV matches
    vLLM's 4-bit weights plus 8-bit KV on perplexity and speed using about half the GPU memory.
- **How it works:** three pieces, and the third is the interesting one.
  - A refinement representation: the extra precision for each low-bit block is stored separately and compressed, not as
    a second full copy of the weights.
  - A selection policy: only the blocks that matter for the tokens in flight get their refinement fetched.
  - Delivery: transfers overlap with decode, and a fetched refinement is reused across decoding steps, so generation
    does not stall waiting for every fetch.
- **What it would take here:** nothing yet, because there is no code. If a release appears, it is a serving-engine
  question for our own hardware rather than a model download: our long-context work already streams the KV cache out
  of pinned host RAM (a 512K-token slot is about 6.2 GB of cache; three of them, or one 1M slot, is 12-18 GB), so
  shrinking the cache bytes with a refinement tier is the same problem StrataFlux attacks.
- **Verdict: watch.** Value: the KV side could fit more or longer sessions in the same RAM, which is exactly the
  constraint on our multi-session backend. Risk: their results are one card at up to 128K on 8B dense models; our
  target is three 512K sessions on a sparse MoE, where prefill volume and cache traffic look nothing like an 8B.
  The measurement that would decide it is ours, not theirs: same retrieval score and decode rate, less RAM.

### 3. skill-distill: turn a good frontier session into a skill an open-weight model can follow (tech)

- **What it is:** [sybil-solutions/skill-distill](https://github.com/sybil-solutions/skill-distill) (MIT, created
  2026-11-21), a skill for Claude Code or Codex that acts as the **teacher**: it reads a session that went well, writes
  a skill for a named **student** (a harness plus a model), then loops until the student reproduces the reference.
  From the [post](https://x.com/0xSero/status/2124035122924232712).
- **What we checked:** the repository, its README, the licence (MIT) and the adapter list. The loop is concrete: write
  the skill; start the student in tmux on a fresh copy of the starting state with the original prompt and the skill;
  diff its output against the reference; fix the skill at the first place the student went wrong; three trials per
  version; a human accepts the result. Adapters: omp tested, Codex and Claude Code written/tested as teacher, pi and
  opencode written but untested (opencode's session log has no parser yet). Requirements are tmux, git, Python 3.10+
  and a student harness pointed at a model; no GPU work of its own.
- **What it would take here:** nothing new to install to *investigate* it, and the pieces exist: all three student
  harnesses we run (opencode, omp, pi) have adapters, and we have graded reference sessions of our own.
- **Verdict: try later, not install-now.** Value: our harness comparison showed the harness, not only the model, moves
  agent results, and this is one way to carry a good run's steps down to a smaller model. Risk: a produced skill
  reproduces *one task*; it is not a general prompt upgrade, and the teacher's judgement is the bottleneck. The
  natural first task is one of our own graded sessions where we already hold the reference output.

### 4. finetune-inkling-2-small: a LoRA recipe for the 594B Inkling (tech)

- **What it is:** [drost-ai/finetune-inkling-2-small](https://github.com/drost-ai/finetune-inkling-2-small) (MIT), the
  recipe behind Tess-4.5-594B-A17B: an agent skill that fine-tunes Inkling 2 Small (594B total, 17B active) with LoRA
  on Tinker, then serves, self-hosts or publishes the result. From the [post](https://x.com/migtissera/status/2123849865679749342).
- **What we checked:** the repository, README and licence (MIT). The useful part is the trap list, which is about the
  model rather than the service: a tokenizer that silently changed from o200k to H200K; experts stored in NVFP4/MXFP8
  that a plain LoRA cannot be merged into without lossy requantization (their answer: adapt attention and unembed only,
  merge in FP32); training caps that count output tokens; and reasoning effort moving a benchmark score 18 points, so
  effort has to be fixed in training and swept in evaluation.
- **What it would take here:** a Tinker account, money for training (their published run was 46.9M tokens for about
  $70), and a 594B model we cannot serve on our cards. We run the 26B Inkling Mini, not this checkpoint.
- **Verdict: no fit now; keep the trap list.** Fine-tuning on rented hardware is a spending decision and we have no
  local rig for a 594B model. The tokenizer and NVFP4-expert notes are worth keeping for anyone adapting Inkling
  checkpoints later.

### 5. OrcaCyber's abliterated Hy4-flash GGUFs (model)

- **What it is:** [orcarouter/Hy4-flash-abliterated-GGUF](https://huggingface.co/orcarouter/Hy4-flash-abliterated-GGUF),
  mixed-precision imatrix quants of an abliterated (refusal-reduced) Hy4-flash, in two builds sized by what stays in
  memory. From the [post](https://x.com/OrcaRouter/status/2124054562202141089).
- **What we checked:** the Hub API and README (with an accepted account; the repository is gated), the file list and
  sizes, the licence, and the engine requirement.
  - Architecture: 220B total, 11.3B active, 42 layers, 512 experts with 16 active, hybrid sparse/sliding-window MLA
    attention, 1M context. Repo total 218.9 GB; Tencent Hy License inherited.
  - **Mix-128G**: three files, 137,949,969,600 B (128.5 GiB) in total, ~94 GB resident, 4.84 bits per weight, KLD
    0.363 and 83.2% top-1 against the abliterated BF16. 63B of the parameters are the Engram hash tables (Q5_0 here),
    which llama.cpp reads from disk row by row, so they do not count against memory. Their KV is small: 30 layers keep
    512-token windows and only 12 keep the whole context as a 576-wide latent, about 17 KB per token in F16, so 32K is
    about 0.6 GB and 128K about 2.2 GB.
  - **Mix-256G**: six files, ~238 GB, ~190.7 GB resident, KLD 0.162, top-1 89.5%. Does not fit here: 190.7 GB of
    resident weights is more than 56 GB of VRAM plus 125 GB of RAM.
  - Abliteration, measured by the publisher: refusal 44.2% average against 94.8% for base Hy4-flash, over-refusal on
    benign prompts down from 10.8% to 5.6%, MMLU 86.7% against 87.0%. Refusal after quantization is not measured yet.
  - Engine: Hy4-flash is not in llama.cpp master. The files were made and tested at the open `hy_v4_flash` pull request
    #32517, branch head `cf70454`; we already keep an image built at that commit.
- **Fit on paper:** Mix-128G's ~94 GB resident weights sit inside our 56 GB of VRAM plus 125 GB of RAM, with the Engram
  table paged from local disk, and the tiny KV leaves room for long sessions. It is the smaller of the two builds by
  their own KLD table, so the quality question is real.
- **Status: not started, and honest about why.** Two things gate it, neither of them a test decision: the Hub gate
  needs the operator's acceptance (one click; the account itself is fine), and the temporary disk that will hold 138 GB
  is still being prepared. Nothing has been downloaded, built or queued, and no test time was taken.

### 6. maya-ik2: a custom Inkling 2 Mini engine that reaches 127 tok/s on one 24 GB card (engine, measured)

- **What it is:** [alesha-pro/maya-inkling-mini](https://github.com/alesha-pro/maya-inkling-mini) (MIT), a Project Maya
  fork whose `maya-ik2` engine runs Inkling 2 Mini with all 3,072 experts resident in 24 GB of VRAM. From the
  [post](https://x.com/superalesha/status/2124102269138346409).
  - Iris's note said no repository was linked; there is one, published the same morning, at VERSION 1.1.70.
  - It replays a token as one CUDA graph (757 kernel launches against llama.cpp's ~7,350), keeps FP8 KV, decodes the
    NVFP4 expert codes in registers because a 3090 has no FP4 hardware, and supports up to 344K context.
- **What we checked:** the repository, licence, build requirements and the vendor's numbers.
  - Vendor: 128.7 tok/s plain decode and up to 212 with the official drafter, against llama.cpp's 57 on the same card;
    prefill 2,742 tok/s at 4K against 1,052. Our own llama.cpp rows on the same model and card: ~52 tok/s short decode,
    ~39 at 100K, ~450 tok/s prefill.
  - Build: `sm_86` only (the engine needs `sm_80` or newer, so there is no V100 build), CUDA 12.8, and it runs the same
    Unsloth UD-Q4_K_XL GGUF we already serve.
- **What we did:** nothing new from this intake — the lab's engine lane had it in hand hours before the bookmark
  arrived, and it qualified itself the same morning at 09:22 through the serving layer, on the same card and model our
  llama.cpp rows use. The image is pinned to the commit, and the entry runs at 311,296 context with an FP8 KV cache
  and the CPU image encoder, so the longest prefill still clears the memory floor.
- **Measured** (one 3090 at 300 W, 311,296 context, FP8 KV, cold prompts, short bench — not agent runs):
  - 127.0 tok/s on a prose prompt and 126.2 on a code prompt (vendor: 128.7). An arithmetic oracle at the lowest
    reasoning effort ran at 184 tok/s.
  - A 95,985-token text prompt: first token at 47.6 s, prefill 2,018 tok/s, decode 105.8 (vendor: 105.6 at 64K,
    90.6 at 128K).
  - A 100,094-token prompt with an image: first token at 97.0 s, prefill 1,990 tok/s, decode 100.8; both retrieval
    codes and the image answer came back right.
  - A 309,197-token prompt with a 4,096×4,096 image: first token at 236.5 s, prefill 1,309 tok/s, decode 71.5; both
    retrieval codes and the image answer right.
  - Fit: 984 MiB free at the tightest point, 73 °C, against our 512 MiB floor.
- **Against our llama.cpp rows** on the same model and card (about 52 tok/s short decode, 39 at 100K, ~450 tok/s
  prefill, 102K context): roughly 2.4x the decode, 2.7x the decode at 100K, 4.5x the prefill and three times the
  context, while still holding the memory floor.
- **Two honest caveats.** The two long short-bench generations (a prose prompt and a code prompt, both carrying a
  nonce) came back as refusals — the model declined them, so the rates are valid but the content is a behaviour
  finding worth watching in agent runs. And the deepest row costs a four-minute prefill, which matters for cold agent
  sessions.
- **Verdict: try, and it wins this comparison.** Further Unsloth-quant Inkling agent tests now run on this entry, with
  the official requant staying on llama.cpp for the control; rows already measured on llama.cpp stay for comparison.

### 9. Surogate 3.7 35B-A3B: worth testing, but the published small export targets Blackwell

- **What it is:** an agent-focused post-train of Qwen3.5-35B-A3B-Base, with vision and a multi-token prediction head,
  from the [bookmark](https://x.com/flaviusburca/status/2124200214047121512).
- **Verified weights:** [BF16 release at `9295c3f`](https://huggingface.co/surogate/Surogate3.7-35B-A3B/tree/9295c3f41334d6ae9fa2903cdb2fa90865f0b23f),
  ungated, actual Apache-2.0 license, 35.95 billion parameters and 71.90 GB across 13 weight shards.
  The config is `qwen3_5_moe`, with **262,144 native context**. The advertised million-token setup uses YaRN
  scaling by four, not a different native context or a retrieval result we have reproduced.
- **Benchmark caveat that matters:** the publisher's **76.4 Terminal-Bench 2.1** score permits one retry of tasks
  that failed the first attempt. The card gives **61.8 for the first attempt alone**. Neither number is our result.
- **Local route:** no GGUF, EXL3 or matching AWQ release found at this check. The official
  [NVFP4 export at `23ff9b2`](https://huggingface.co/surogate/Surogate3.7-35B-A3B-NVFP4/tree/23ff9b22194dd921109fb8bad1298b229105613e)
  is only 23.83 GB including its prediction head, but its card explicitly targets Blackwell; that is not proof
  of support on a 3090 or V100. The linked Surogate engine's supported builds likewise do not establish our cards.
  A more plausible route is BF16-to-GGUF conversion: current llama.cpp
  [registers this exact architecture](https://github.com/ggml-org/llama.cpp/blob/b052049276778d47eb216739c9e1537d764c5585/conversion/qwen.py#L860)
  and has its text and image implementations. Exact checkpoint conversion remains untested.
- **Fit estimate, not a result:** a Q6-class model would be roughly 29.5 GB before selective tensor precision;
  the full-attention portion of an 8-bit key/value cache is about 0.98 GiB at 102,400 tokens, plus recurrent state,
  workspaces and image handling. That makes a V100 Q6 trial plausible, with Q5 as a fallback, but the actual file
  and longest prefill must decide it. We have not measured tokens/s or time to first token for this model.
- **Verdict: try; research and backlog handoff completed, execution not started.** The storage server cannot
  hold the original, and the fast scratch disk cannot hold the original plus intermediate and final conversions
  together. Prepared temporary model overflow provides a source-storage option; the lab owner has the concrete
  conversion/staging and next-slot decision. The existing light-testing work keeps its cards, and the old whole-GPU
  queue stays paused. No weights, build, case ID or inference started by this intake.

### 10. inference-optimisation-skill: useful reference, not an install-now performance upgrade

- **What it is:** [Sybil Solutions' tuning skill](https://github.com/sybil-solutions/inference-optimisation-skill/tree/fda968e7fc1996aa23c67139c755fe541c9d4be0),
  MIT, source-only with no tags, releases or binary assets at inspection. From the
  [bookmark](https://x.com/0xSero/status/2124238286457917649).
- **How it works:** estimate bandwidth and compute ceilings; change one variable; measure between two control runs;
  keep the failures in a ledger; account for speculative acceptance; then qualify retrieval and full-context
  concurrency. It ships a Python benchmark, memory and queue helpers, and a lever catalogue, not a new inference engine.
- **What we checked:** README, license, procedure and benchmark implementation, with a separate read-only audit of
  helpers and linked author evidence. The default benchmark uses six short decode samples, 512 output tokens,
  four concurrent requests and roughly 4K/32K prefill. Long-context checks are opt-in. Several written acceptance
  steps are not automated, and there is no authentication or native serving-claim integration in the benchmark.
- **What it would take here:** selectively adapt its ideas inside our existing measured tuning workflow, not run
  its launch/stop configurations against a live server. That needs no new service or network exposure. Its private
  queue lock does not coordinate with other lab clients, and it does not enforce our per-card memory floor.
  Persistent compiler caches are not disk key/value caches, but engine-default conversation spilling is not audited
  or disabled by this skill either.
- **Verdict: watch/reference; not installed.** Much overlaps our existing procedure. The useful ideas are explicit
  control runs and speculative-cost accounting; the risks are disrupting active tests and optimizing a short fixed
  benchmark instead of real agent work. The post's blanket “30 reports, 30%–5x” claim was not verified. The README
  links selected author-supplied measurements, which are evidence to inspect, not speedups promised for our setup.
