## Inkling 2 Mini CUDA speed fork — noon research snapshot; measured update below

Source: [Iris's bookmark note](../../iris/2026-11-22-steady-alex-bookmarks.md), [post](https://x.com/JacksonAtkinsX/status/2124165896948347118), [upstream fork](https://github.com/realugbun/llama.cpp/tree/2eb2530ec4da95453e8ea7d68f937da174dfe799).

No weights, builds, case IDs or GPU tests started in this intake. The existing V100 maze run and the 3090 daily driver were left alone; the old whole-GPU queue remains paused.

### What we checked

- MIT licence, branch `inkling2-speed`, pinned head `2eb2530ec4da95453e8ea7d68f937da174dfe799`. No published releases or binary assets. Its exact upstream base is `e50c254a22c590c9d2a60db86690d48d42497e2b`: four code commits followed by four documentation/media commits, not four commits total. [Immutable comparison](https://github.com/realugbun/llama.cpp/compare/e50c254a22c590c9d2a60db86690d48d42497e2b...2eb2530ec4da95453e8ea7d68f937da174dfe799).
- The code actually adds normalized depth-state reuse, graph scheduling to make operation chains contiguous, eleven CUDA fusion variants, and a narrow-row padding optimization. The new fusion code and tests are present, not just a benchmark chart.
- Source inspection found no unconditional sm_80-only requirement in the added kernels. Both sm_70 and sm_86 are plausible **CUDA 12** targets; compilation and native target coverage remain unverified. CUDA 13 is not a V100 build path.
- No new disk KV/session-persistence default appears in this delta. Existing optional file caches and logging are separate inherited features, not an excuse to enable them.

### What the speed claims mean

The author's README reports **V100 Q4_K_XL decode +59–68%** and **1.6–4.9× pp512 throughput** at increasing context depths, with full GPU offload, flash attention and **F16 KV**. Its 5060 Ti IQ1_S rows report +37–39% decode and 2.0–4.1× pp512 throughput. These are short `llama-bench` measurements; pp512 at 128K context depth does **not** measure the total time to ingest a fresh 128K prompt. Time to first token is not supplied. The largest depth on each card uses ubatch 256 because 512 runs out of memory on both builds.

These claims do not predict our V100's Mainline_Support UD-Q8_K_XL with Q8 KV, or our 3090's Maya engine. In particular, this is not evidence that the fork beats the already-qualified Maya path on the 3090.

### Correctness is still a measurement, not a slogan

The added backend-chain tests compare against unfused CPU operations with numerical tolerances. The code carefully preserves rounding/reduction order in several paths, but an alternate MIX path and the README acknowledge numerical differences. The author's nonzero Kullback–Leibler divergence figures are useful evidence to investigate, not a bitwise-identity proof. We found no attached GitHub check runs on the pinned head or its four code commits. The README's 20,882 passing tests are an attributed third-party AMD/HIP report, not our CUDA result.

The fusion dispatcher and padding change are not restricted by a model-architecture gate, so “other models unaffected” is not an isolation guarantee enforced by the source.

### What it would take here

Our V100 deployment uses mainline b12622 and **Mainline_Support UD-Q8_K_XL**. The fork inherits the merged NVFP4 loop-scale correction, [llama.cpp #32704](https://github.com/ggml-org/llama.cpp/pull/32704). Older root-layout Unsloth files that need b12588 are a different engine/weight pair; a matching quant label is not enough to swap them.

Next action is with the lab's serving owner: build the exact upstream base and fork with the same CUDA 12 compiler/runtime and explicit `70;86` targets, including the added backend tests (the stock server Docker target disables them). Then stage a separate candidate and compare in a granted V100 test boundary, using the **same existing verified weights**, native reasoning controls, Q8 KV, context, batch/ubatch, cache warmth and power policy. Report sustained short/deep decode, full cold-prefill latency/time to first token, actual free VRAM, retrieval, tools and an image check. No new service, network exposure or weight download is required. No adoption or GPU slot is claimed by this intake.

The active V100 run is a real scheduling constraint; the completed port project is not. The build and matched comparison are recorded as backlog work, not executed tests.

## Afternoon: PCIe switch-card expansion — watch; useful expansion option, not five independent host links

Source: [Iris's afternoon append](../../iris/2026-11-22-steady-alex-bookmarks.md), [Caveman Tech's post](https://x.com/Cavemtech/status/2124390517823660317), [Broadcom PEX88096](https://www.broadcom.com/products/pcie-switches-retimers/expressfabric/gen4/pex88096), [manufacturer's product brief](https://docs.broadcom.com/doc/BC-0484EN).

**What it is:** an active PCI Express packet switch with a host x16 link and enough downstream lanes for five x16 device links. Unlike passive bifurcation, it creates separate downstream links rather than dividing sixteen physical lanes among five sockets. Two correctly wired x8 cable bundles can carry one x16 link; matching connector shapes alone do not establish cable pinout, clock/reset wiring or signal integrity.

### Verified claims and limits

- Broadcom documents **96 data lanes plus two x1 management ports**. That explains why the product page says 98 lanes while the useful topology is 16 upstream + 80 downstream. This is a real shipping chip family, not a new software release. No model, executable, open-source licence or install is involved in this intake; the commercial board's exact revision/firmware and support package remain unspecified.
- The author's later replies identify a **PEX88096 / SFF-8654 expansion-card listing** and disclose an affiliate link. That chip is **Gen4, not Gen5**. A Gen5 motherboard does not make a PEX88096 board Gen5; that requires different switch hardware and compatible cables/risers. The original post's generic “Gen4/Gen5” wording should not be treated as this listing's specification.
- Five Gen4 x16 downstream links still share **one Gen4 x16 uplink**. Calculated encoding-adjusted ceilings are **31.51 GB/s in each direction for the uplink**, or about **6.30 GB/s each if five devices share it equally**, before packet overhead. These are theoretical limits, not measured throughput. The full post itself acknowledges the roughly 5:1 oversubscription; Iris's short summary omitted that important qualification.
- GPU-to-GPU traffic can remain inside the switch **only when the cards, driver, platform and engine support peer access**. A switch is not NVLink, does not pool VRAM automatically, and does not guarantee CUDA peer-to-peer support. [NVIDIA's guide](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html) requires checking peer-access capability and documents topology, IOMMU and PCI Access Control Services constraints. No isolation, driver or firmware settings were changed or proposed for bypass.
- SSDs consume downstream lanes too: five x16 GPUs already use all 80. Twenty x4 drives is an alternative allocation, not an additional twenty drives alongside those GPUs. Sharing the switch also does not automatically make storage-to-GPU transfers bypass host memory.
- **The approximately $700 is the author's estimate, not a verified delivered quote.** It excludes GPUs and drives; power supplies, suitable cooling/chassis, correct risers/cables, shipping/tax, firmware support and a return path still matter. A board capable of fan-out does not certify the whole assembly.

### Local lens

The interesting use is a future lane/slot expansion on the **GPU host**, especially for weights that stay resident in GPU memory. Our read-only topology check found the V100 behind a chipset path at **Gen3 x4**, while the 3090 has an x16 link. Peer reads/writes between the current pair report unsupported. A suitable switch on the CPU-connected slot could remove that particular narrow physical path, but neither working peer access nor an inference speedup follows from the diagram. The idle 3090's sampled low link speed is not a loaded-bandwidth result.

RAM-offloaded experts and host-resident long-context state still cross the shared uplink, so “fine for inference” depends on the engine and placement. A switch does not replace our need for model-storage capacity, adequate host RAM or engine compatibility.

**Verdict: watch for a concrete expansion build, not a purchase recommendation now.** It would be hardware work on the GPU host, not a container or new network service: exact board/firmware, motherboard enumeration and address-space support, matched cables, power and cooling first, then link-width/peer-access and workload measurements if an upgrade is separately authorized. Nothing bought, installed, downloaded, built or queued; no active test, model, claim or host setting changed.

## Result update: the Inkling CUDA fork is built and short-benchmarked, not serving-qualified

The lab's serving lane completed the matched pair after the noon intake. We read back its exact build receipt and original benchmark output rather than repeating the tests.

Both arms use CUDA 12.8.1 / GCC 13.3, explicit sm_70 + sm_86 targets, the same existing Mainline_Support **UD-Q8_K_XL** pack, Q8 K/V, full GPU offload, flash attention, batch 512 and ubatch 128. The control is the exact upstream base `e50c254a22c590c9d2a60db86690d48d42497e2b`; the candidate is `2eb2530ec4da95453e8ea7d68f937da174dfe799`. Model-free CUDA output reports the head's selected Inkling operation tests **82/82 passed** on the V100. This is tolerance-based backend coverage, not proof of full-model equivalence or agent quality.

Short `llama-bench` results, two repetitions per arm:

- Prompt processing, 512 tokens: **345.32 → 417.75 tokens/s**.
- Prompt processing, 4,096 tokens: **311.69 → 425.56 tokens/s**.
- Prompt processing, 32,768 tokens: **237.44 → 408.36 tokens/s**.
- Standalone 128-token generation: **28.64 → 42.30 tokens/s**, about **48% faster** than the exact-base control.

The recorded regime was V100 250 W with the neighboring 3090 idle. These are synthetic benchmark rates, **not agent-run rates**. **Time to first token was not measured.** These commands use separate `-p` prompt-processing and `-n` generation tests: they do not establish sustained generation at a 32K or 131K context depth. No extrapolated agent-task completion time is claimed.

**Status:** built, staged and short-benchmarked. Candidate serving entries are prepared but not activated. Router-served correctness, tools/vision, actual near-200K free-VRAM fit, cold first-token latency and agent tests remain outstanding.
