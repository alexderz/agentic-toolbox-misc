### Strata v0.2.16: Strata's own engine code (tech update)

- **What it is:** a new release of [Strata](https://github.com/Niko1221/Strata) (MIT), the local inference app and
  engine that serves our current daily-driver model (an Orca Flash-Next fine-tune, on Strata 0.2.15 since Nov 16).
  Release [v0.2.16](https://github.com/Niko1221/Strata/releases/tag/v0.2.16), commit `64524fb9`, published
  2026-11-18 21:57 UTC, 724 commits after v0.2.15. Engine and control program are both 0.1.62.
  Bookmarked post: https://x.com/coldniko/status/2123202426609999937
- **What we checked (GitHub, at the tag):**
  - **Engine code.** llama.cpp's MMQ prompt kernels are gone from the tree. Every CUDA build compiles Strata's own
    prompt kernels. ggml is still there for some CPU paths, but now vendored in `engine/third_party/strata-ggml`, at
    the same llama.cpp commit (`3cf03257`) as 0.2.15, so nothing is downloaded at build time.
  - **Same answers?** Upstream reports the same tokens as 0.2.15 on its 10 test prompts on six GPUs (RTX PRO 5000,
    P100, R9700, Arc A750, M5 Max, Strix Halo). Neither of our cards (RTX 3090, V100) is in that list, so token parity
    on our hardware is unproven.
  - **Speed claims that touch us:** a 26,000-token prompt on a Tesla V100 went from 17.5 s (engine 0.1.58) to 15.1 s.
    There is no RTX 30-series number in the notes.
  - **Server behaviour.** The `undeclared_tool_calls` setting (`text` or `call`) still exists in the server, so our
    `call` setting carries over. The new "a tool call that cannot run no longer ends the turn" fix is in Strata's own
    chat agent, not in the API server our harnesses use.
  - **Build layout moved.** Top-level folders are now `engine/`, `app/`, `terminal/`, `docs/`, `tools/`. The server is
    `terminal/serve/server.py`; the engine builds with `cmake -S engine`. Upstream ships an official source-build
    Dockerfile (`tools/docker/Dockerfile.src`) that covers a CUDA 12 build for older cards including the V100 (sm_70).
    Our own build recipe assumes the old layout, so it needs rework before it can build this tag.
  - **Ready-made binary:** `strata-engine-0.1.62-linux-x86_64-cuda-cuda12.tar.gz` (sha256 `450abcbd…c4d7`) is
    published with the release, an alternative to a source build.
- **Verdict: relevant; qualify it.** It is the engine of our daily driver, the kernel change is big enough that our
  own numbers can move either way, and the V100 prompt speedup is directly useful. The standard check is an A/B on the
  daily-driver model: same flags and power cap as the 0.2.15 production serve, comparing tokens/s, time to first
  token, long-prompt prefill, retrieval near the full context and token agreement with 0.2.15.
- **Started:** nothing yet. The GPU host has been offline since the evening of Nov 18, and its 24 GB card is in use
  for the daily-driver test suite when it is up. The qualification is handed to the lab owner (build recipe rework,
  then the A/B in a gap the testing side grants). Results will be added here when they exist.

### maya-hy4f: Hy4-flash on RTX 3090s, with a runtime "uncensored" vector

- **What it is:** an engine for Tencent's Hy4-flash (220B MoE, 512 experts per layer, 16 active, a 63 GB Engram
  n-gram table, vision, 262K context) built on Project Maya's kernels by Alexey Fateev, plus a weights repo with a
  4 MB refusal-direction file. Bookmarked post: https://x.com/superalesha/status/2123520167611428988 ·
  engine [alesha-pro/project-maya, branch `hy4-flash`](https://github.com/alesha-pro/project-maya/tree/hy4-flash)
  (MIT) · weights [alesha-pro/Hy4-flash-Uncensored-GGUF](https://huggingface.co/alesha-pro/Hy4-flash-Uncensored-GGUF)
  (Tencent Hy License, same file as Tencent's own repo).
- **What we checked:**
  - **Pins.** Engine commit `cbe0a1fe` (a fork of mw00/project-maya at 1.1.66 with its own `maya-hy4f` binary; it is
    not the `maya-hy4` engine in mw00's v1.1.68 release, which is what we already run Hy4-flash on). Weights revision
    `239e9f9b`, not gated.
  - **How "uncensored" works.** The weights are stock. The engine reads the vector file and, for every layer and each
    of Hy4's four hyper-connection streams, projects the recorded refusal direction out of the residual stream as it
    runs. Delete one environment line and you have the stock model again; a scale setting gives anything in between.
    The author reports refusals dropping from 139 to 32 out of 146 held-out harmful prompts (thinking off), 22 to 3
    of 24 (thinking on), with top-token agreement to the stock model of 85.7% against an 88.3% run-to-run noise floor.
    We have not measured any of that yet.
  - **Files.** Two complete sets: a Q3_K trunk (86.2 GB, AngelSlim's Q3_K with the MTP layer requantized) or an
    IQ2_XXS trunk (51.1 GB, AtomicChat's IQ2 experts spliced in), each plus the same 63.4 GB Engram table.
  - **The Engram table we already have is the same data.** Our existing Maya-L download of Hy4-flash has an Engram
    file 32 bytes longer. Its tensor data is byte-identical: the author's 192-byte header followed by our file's data
    hashes to exactly the author's published sha256. The engine only reads metadata from the first shard, so only a
    trunk download is needed here.
  - **Not compatible with our Maya-L trunk.** The engine has no IQ4_XS kernels, and Maya-L's experts are IQ4_XS, so the
    vector cannot simply be turned on for the model we already serve.
  - **Disk writes (code read).** No KV cache to disk. The engine writes routing statistics on exit if told to, and
    debug dumps only on request; its "KV snapshots" for returning to an earlier conversation live in RAM.
- **What it would take here:** the single-card path fits our box best: the 24 GB RTX 3090 alone, the Q3_K experts in
  about 78 GiB of RAM, and the Engram table read from local NVMe. That leaves the 32 GB V100 free for other work. The
  two-card path wants 137 GiB of RAM (we have 125), and our second card is a V100 (sm_70), which upstream never tested.
  Upstream's single-card numbers (37-54 tok/s decode, ~1,500 tok/s prefill) are about twice the decode and six times
  the prefill we measured today for Hy4-flash on the mw00 engine across both cards (~19-23 and ~240, short bench). The
  catch to measure: upstream leaves only about 0.5 GiB of VRAM free on one card, right at our 512 MiB floor.
- **Verdict: try.** It is the model we are testing right now, the same weights (plus a cheap, reversible way to take
  most refusals out, which Alex rates as a bonus), on a path that may be much faster on our hardware.
- **Started:**
  - Engine image built from the pinned commit for the RTX 3090 (sm_86, CUDA 12.9, portable AVX2 CPU code); it starts
    and prints usage, all libraries resolve. A second build that also targets the V100 was started.
  - Download of the Q3_K trunk started (throttled, sha256 checked); the vector, vision projector, configs and routing
    profiles are already downloaded and verified.
  - Not run yet: the test goes to the lab owner, to run in a gap in the current Hy4-flash test suite. Planned rows:
    fit after the longest prefill, tokens/s and time to first token, retrieval near 100K, the quality stage, then a
    refusal check with the vector on and off, and the same agent tests the mw00-engine run got, so rows compare.

### QuixiInfer: a Rust engine for DeepSeek V4.1 Flash on one GPU

- **What it is:** [QuixiAI/QuixiInfer](https://github.com/QuixiAI/QuixiInfer) (MIT) by Eric Hartford: a from-scratch Rust
  engine that runs one model, DeepSeek-V4.1-Flash-1017, on a single GPU at 256K context with CPU and NVMe offload; the
  author reports ~25-30 tok/s with up to 3 concurrent requests on an RTX 5090 and asks for testers on other cards.

### Results: maya-hy4f (8pm item), added 2026-11-20

- **Qualified on our 24 GB RTX 3090 alone** (300 W cap; the 32 GB V100 is not used, because this engine has no sm_70
  build). Setup: the Q3_K network trunk on local NVMe, with the Engram table read directly from NVMe. We reused the
  Engram file we already had from Maya-L, and it loaded unchanged.
- **Fit:** 924 MiB of VRAM free after a 100,254-token prompt, with 131,072 tokens of context served.
- **Short benchmark (not an agent run):** 23.9 tok/s decode on chat and 26.8 tok/s on code, with a time to first token
  of about 2 s. With thinking on: 23.1 tok/s.
- **Retrieval:** both 26K and 100K pass. Prefill runs at about 1,340 to 1,420 tok/s; time to first token is 19.6 s at
  26K and 70.7 s at 100K.
  - For comparison, the earlier engine's both-card Maya-L build managed about 19-23 tok/s decode and about 240 tok/s
    prefill. Upstream reports 37-54 tok/s decode on its own box (an EPYC with 8-channel RAM), and we see about half of
    that.
- **Refusal vector (an over-refusal check, not a harmful-request set):**
  - Stock refused 2 of 64 harmless prompts and 0 of 24 harmless lookalikes.
  - With the vector on, it refused 0 of 64 and 0 of 24.
  - Decode stayed about the same with it on (22.1 / 27.1 tok/s).
- **Agent tests:** test 7 scored 8/10 in both Oh My Pi and OpenCode, and test 1 scored 5/5 in OpenCode. These are agent
  runs, and their rates are not comparable with the short benchmark above.
- **Where it stands:** this engine now serves the primary Hy4-Flash configuration in our testing. The earlier Maya-L
  results stay valid as supplementary rows.
