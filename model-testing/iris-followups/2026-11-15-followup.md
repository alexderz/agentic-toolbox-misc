## 8am run: Nace.AI "Weight Space Programming" Qwen GGUFs (backlog)

- **What it is:** [Nace.AI](https://huggingface.co/nace-ai) released GGUF quants of four Qwen models, made by letting
  frontier-model agents edit the precision of individual tensors in an existing GGUF, measure the KL divergence from
  the BF16 model, and keep or revert each edit. The files use only stock llama.cpp tensor types (a mix from about 2 to
  8.5 bits per weight), so they load in an unmodified llama.cpp.
- **What we checked on Hugging Face** (all Apache-2.0 on the cards, not gated):
  - [Qwen3.8-Flash-Next-GGUF](https://huggingface.co/nace-ai/Qwen3.8-Flash-Next-GGUF) @ `50e8661b`: one IQ4_XS file
    (3 shards, 93.4 GB). Their mean KL is 0.063 against 0.073 for Unsloth's UD-IQ4_XS of the same size. This is the
    interesting one: Flash-Next is our daily driver, and 93 GB fits the GPU host's experts-in-RAM tier.
  - [Qwen3.8-27B-GGUF](https://huggingface.co/nace-ai/Qwen3.8-27B-GGUF) @ `b3bd0ba0`: Q4_K_XL, 17.3 GB, built from
    Unsloth's UD-Q4_K_XL. By their own numbers it ties Unsloth at 512 tokens and wins by 0.0002 KL at 128K, which is
    too small to matter. Low priority.
  - [Qwen3.6-35B-A3B-GGUF](https://huggingface.co/nace-ai/Qwen3.6-35B-A3B-GGUF) @ `c9e12d29`: IQ3_XXS 14.3 GB and
    Q3_K_S 15.3 GB. These can join the KL-divergence check already staged for MACaQ-R on the same model
    ([Nov 12](2026-11-12-followup.md)).
  - [Qwen3.5-9B-GGUF](https://huggingface.co/nace-ai/Qwen3.5-9B-GGUF) @ `16910a01`: 3.4 to 4.7 GB. We don't test a
    9B, so we're skipping it.
- **How to read the claim:** all the quality figures are the vendor's KL and top-1 numbers on their own held-out text.
  The MMLU chart in the post shows every file within half a point of its rivals and of BF16, so on task scores the
  quants are level. KL to BF16 is a fair way to compare quants, and it's cheap to reproduce, so we'll measure it
  ourselves before running any long tests.
- **Verdict:** backlog, deferred while the port work has the GPU. When testing resumes, the first step is our own
  KL-divergence measurement: Nace's Flash-Next IQ4_XS against the Unsloth v3.1 files we already hold, plus the 35B-A3B
  files added to the MACaQ run. The full Flash-Next performance comparison follows only if their KL lead holds up
  on our text. Nothing has been downloaded.
- **Also in the post:** [Drex Max v1](https://huggingface.co/nace-ai/drex-max-v1) (27B, Nace.AI Open RAIL-M), a
  "decision model": it returns a probability for each option you give it in one forward pass and never generates
  text ([paper](https://arxiv.org/abs/2611.07854)). It needs Nace's own loader, which makes some attention layers
  non-causal. Watch: if we test it, it belongs next to the Perplexity decider bench, not in agent coverage.

## 4pm run: Inkling-2-Small GGUF, ~150 GB IQ2_XXS mix (backlog)

- **What it is:** a community GGUF of Thinking Machines' [Inkling-2-Small](https://huggingface.co/thinkingmachines/Inkling-2-Small)
  (594B-parameter mixture of experts, 17B active, 1M-token context, text and image input), published as
  [peasantsmith/Inkling-2-Small-GGUF](https://huggingface.co/peasantsmith/Inkling-2-Small-GGUF)
  ([post](https://x.com/PeasantSmith/status/2122025487186940397)). The routed experts are rounded with per-expert
  error feedback (GPTQ-style), layer by layer; the bits for each layer's down projection come from a sensitivity sweep
  (mostly IQ1_S, some IQ2_XXS); attention stays at Q8_0 and the output head at Q6_K.
- **What we checked:** revision `929dc580` on Hugging Face, Apache-2.0 (base too), not gated. Four language-model shards
  totalling 150.0 GB, a 0.66 GB vision projector and a 3.4 GB multi-token-prediction (MTP) block. We read the first
  shard's header: architecture `inkling2`, 48 layers, 8 KV heads, a sliding window of 1,024 on five of every six
  layers, and the per-layer bit allocation embedded in the metadata matches the card. The quality figures (94.3% same
  top token as the original model, mean KL divergence 0.114, perplexity +3.6%) are the author's, on their own held-out
  text; we have not measured them.
- **Why it matters here:** this is the first Inkling 2 file that fits our experts-in-RAM tier on paper. Yesterday's
  [Tess-4.5-594B entry](2026-11-14-followup.md) found the smallest Unsloth build at 171.7 GB, too big. At 150 GB, with
  about 6 GB of non-expert weights and under 2 GB of 8-bit KV cache at 100K tokens (only one layer in six keeps the full
  context), roughly 44 GB of experts fit on the two GPUs above our free-memory floors and the other ~100 GB sit in the
  125 GB of system RAM. Tight, unmeasured, and it will be experts-in-RAM speed, not GPU speed.
- **The catch: engine layout.** The card says these files run on llama.cpp
  [PR 32187](https://github.com/ggml-org/llama.cpp/pull/32187) (still an open draft, head `a45f6626`, last commit
  Nov 13). Inkling 2 support actually landed in llama.cpp master through a different pull request,
  [PR 32217](https://github.com/ggml-org/llama.cpp/pull/32217) (merged Nov 14 as `5c008e00`), and it uses different
  tensor names: master has no `shortconv_k_dyn`, `attn_rel_proj` or `attn_q_in_norm`, which these files contain. So
  the files will not load in a stock llama.cpp release; they need the draft PR built from source. The author says files
  for the merged layout will follow. Neither path is proven on the V100 (sm_70) yet, and we would need both cards.
- **Verdict:** backlog, deferred while the port work has the GPU. Nothing downloaded or built. When testing resumes:
  prefer a merged-layout re-release (stock llama.cpp, no draft PR); otherwise build the PR 32187 head for sm_70 + sm_86.
  Then a viability case: load and fit, tokens/s and time to first token, retrieval near 100K, and the quality stage.
  Our runner has no image stage yet, so it would be text-only; the MTP draft block isn't used by either loader. Storage
  is also a blocker for now: the NAS is short of room for another 154 GB until new drives arrive. The base model is
  already on our hosted free-model watch.

### Unharnessed: a coding-agent harness with one tool, a persistent Python REPL

- **What it is:** an open-source coding agent whose model gets exactly one tool, `ipython`, a persistent CPython
  REPL; reading, searching, editing and running commands are all Python the model writes in that session.
  [Iris note](https://github.com/alexderz/agentic-toolbox-misc/blob/main/iris/2026-11-15-steady-alex-bookmarks.md) ·
  [code](https://github.com/unharnessed-agent/Unharnessed) · [site](https://unharnessed.dev/en).
- **What we checked:** the GitHub repo at `fe2cf281` (Nov 15). MIT licence (the file also credits Prime Intellect
  and Mario Zechner for portions), created Oct 2, about 140 stars. The only release assets are macOS arm64 VS Code
  extensions (`vscode-v0.0.3` and `v0.0.4`, both Nov 15); on Linux you build it from source with Cargo
  (`cargo build --release -p uh-cli --bin unharnessed`).
- **How it works:** a Rust host handles the agent loop, compaction, goals, provider retry and failover, sessions, and
  speaks the Agent Client Protocol (ACP) over stdio. The VS Code extension is one ACP client; there is also a headless
  `-p` CLI. The kernel is one long-lived Python process in a uv-managed venv. Variables, helper functions and
  background processes survive compaction, so a 40,000-line log can stay in a variable while only the lines the
  model needs go into its context. The static system prompt is about 1,700 characters. It deliberately leaves out
  sub-agents, memory and permission prompts. It never asks before running a command, and the README says plainly that
  the kernel is not a sandbox and you should run it in a container or VM. Providers: subscription sign-ins (Claude,
  ChatGPT, Copilot, Google, Grok), about 25 API providers including OpenRouter, and local OpenAI-compatible servers
  (llama.cpp, vLLM, Ollama, LM Studio). An "autonomous" mode keeps going until your own gates (tests, lint) pass.
- **The benchmark claim:** the site says 47 of 66 Terminal-Bench 4.0 tasks with Claude Opus 5.5 (about 71%), one
  run, self-reported. The site's own cost-versus-score chart is labelled "Placeholder data", and we could not read the
  official leaderboard (it renders in JavaScript), so treat the "state of the art" claim as unverified.
- **What it would take here:** a Cargo build plus uv, run inside a container with only a scratch checkout mounted,
  pointed at the GPU host's llama.cpp endpoint. No new service or network exposure. Nothing was installed.
- **Verdict: watch.** The interesting question for this lab is whether local models do better or worse with one REPL
  tool than with a full tool list. Small local models are exactly the "less capable" end the authors say needs more
  rails, which makes that a real test, not a foregone conclusion. Three things stand in the way today. Our agent tests
  run through T3 Code with OpenCode underneath, and a second harness would need its own harness identity in the
  results. The project is six weeks old and ships macOS-only binaries. And the GPU is busy with the port work.
  Backlog idea for when testing resumes: an A/B on one local model, the same agentic tasks through OpenCode and
  through Unharnessed (containerised).
