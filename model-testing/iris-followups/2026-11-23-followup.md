## GPU-to-GPU P2P guide for GeForce cards — do not install

Source: [post](https://x.com/kamilskowron/status/2124856757675549143), [guide](https://github.com/Cinderella-Man/how-to-enable-p2p-on-nvidia-gpus) (no licence file on that repo), patched modules [Cinderella-Man/geforce-dynbar1-p2p](https://github.com/Cinderella-Man/geforce-dynbar1-p2p) at the guide's pin `e5ad35de7fe517ffa85ff6d057777be7cb9ff465`, a fork of [noon-at-cgn/geforce-dynbar1-p2p](https://github.com/noon-at-cgn/geforce-dynbar1-p2p) on NVIDIA's open kernel modules `615.71.09`.

**What it is.** A procedure for making consumer GeForce cards copy GPU-to-GPU over PCI Express instead of bouncing every copy through the computer's main memory. Stock GeForce drivers report no peer access, so CUDA and NCCL stage those copies through host RAM. The guide swaps only the open kernel modules for a patched build of the same version; the userspace driver stays the distribution package. Copies then go card to card, if the platform actually carries the traffic.

**How it works, and what it measured.** For RTX 30 cards the path is Ubuntu 26.04, the packaged NVIDIA 615 open driver (not 595), CUDA 13.5, Secure Boot off, Above 4G decoding and Resizable BAR with BAR1 at least as large as VRAM, and `iommu=pt`. The patch grows BAR1 dynamically and forces peer capability, skipping the driver's chipset and topology checks. The author's own review of the non-NVIDIA diff at that pin says it found no malicious code; we did not re-audit or load it. Their published numbers, on a two-3090 rig with one card in a slow x4 slot, are about 12–13× lower copy latency (about 19 µs to about 1.5 µs) and +46–70% on the two-way exchanges (NCCL all-reduce about 1.88 to 2.75 GB/s). One-way traffic barely moves, because the x4 slot caps it either way. They are careful that this is the exchange itself, not a whole model: on another machine, vLLM was anywhere from no faster to 32% faster. Zero errors in about 1.5 TB of test copies is their integrity-test result, not ours.

Pascal and Volta are a different path. The open driver cannot load them (no GSP processor). Two Tesla V100s get peer access from NVIDIA's stock closed 580 driver once the IOMMU is in passthrough; without that, the author's test logged IOMMU faults and the copies "succeeded" without the data arriving. The same note says the driver refuses different-generation pairs.

**Local verdict: no value on this pair. Do not install.** The GPU host is not Ubuntu, not driver 615, and Secure Boot is on. It has one RTX 3090 and one Tesla V100, not two GeForce cards and not two V100s. A read-only check shows peer reads and writes unsupported both ways, the link between the cards going through the CPU host bridge. The 3090's BAR1 is 256 MiB; the V100's is already the full 32 GiB. The V100's link is PCI Express generation 3 by 4 lanes, so even a working peer path would be capped near 4 GB/s. The open-module patch that enables GeForce peer access cannot load the V100, and the stock driver already refuses this mixed pair. Our serving splits layers inside llama.cpp or Strata; it is not an NCCL tensor-parallel all-reduce. Turning on IOMMU passthrough, disabling Secure Boot, or replacing kernel modules would be a host change, and the guide's own V100 write-up shows silent data loss if passthrough is wrong. Nothing installed. Worth another look only if this box ever has two same-generation GeForce cards on CPU lanes.

**The file that could run.** [bartowski/Ling-3.2-air-GGUF](https://huggingface.co/bartowski/Ling-3.2-air-GGUF) at `2073edb5da4296cb37b334584b858aa6141e352f`, MIT, quantized with llama.cpp `b12600` (published 2026-11-20). ### deslop-please — watch; we have no Rust of our own to run it on

Source: [post](https://x.com/MOVNTDQ/status/2124947434078155043), repo [deterministic-machines/deslop-please](https://github.com/deterministic-machines/deslop-please) (MIT, created 2026-11-22, v0.1.3 released 2026-11-23, published on crates.io).

**What it is.** An opinionated linter for code structure, built on the argument in "A Philosophy of Software Design": modules should be deep and their interfaces narrow. Six checks run on a Cargo workspace: module cycles, tangles (two modules that each know something the other owns), field leaks (a type's fields or functions used from outside it), shallow modules (too many small functions exposed), wide directories and long files. It reads rust-analyzer's index of the workspace, cached under `target/deslop-please/` with build scripts off so nothing is compiled, and it has to find rust-analyzer on the path. It exits like `cargo clippy`. An `--allow` file mutes existing debt so new errors still fail; `--update-allow` rewrites that file.

**What the author claims.** 23 structural issues found in bbtree, all fixed, and fewer tokens per task afterwards because related context ends up closer together. That is his repository and his number; the README's own sample output is a joke ("65535 errors, well done!").

**Local verdict: watch.** The checks are Rust-only: a Cargo workspace plus a rust-analyzer index. Our own code is Python (the lab's runner and grading tools) and TypeScript (the toolbox projects), so there is nothing here to point it at. The one Cargo tree on the GPU host is a clone of someone else's engine, owned by another lane; linting it would measure their code, not ours. If a Rust project of ours appears, `cargo install deslop-please` plus rust-analyzer is a minutes-long try with no GPU and no service behind it. The four rules themselves are language-neutral, but nothing here lints Python or TypeScript, and writing that is not intake work.

### Turing memory-window and peer-access method — no value on this pair

Source: [post](https://x.com/kamilskowron/status/2124906227826073754), with the method written up in [the same guide](https://github.com/Cinderella-Man/how-to-enable-p2p-on-nvidia-gpus/blob/main/docs/turing.md) (no licence file on that guide repo; the resize tool, [noon-at-cgn/geforce-bar1-resize](https://github.com/noon-at-cgn/geforce-bar1-resize), is MIT and pinned at `53466608`).

**What it is.** RTX 20 and GTX 16 cards never got Resizable BAR: the first memory window (BAR1) is 256 MB, so the CPU or another card sees only a keyhole into video memory. The method widens that window at every boot without flashing anything. First it removes the card's USB-C and UCSI functions (`0c0330`, `0c8000`), which sit in the same address window and make the resize fail with "No space left on device"; then geforce-bar1-resize arms a frame-buffer size override in the card's PCI config space, and after a reboot the window covers the whole card. Peer access is switched on per card in a patched open-module driver, and because CUDA itself refuses peer access between two *different* chips, a small preload shim sits in front of libcuda. The card's USB-C ports stop working while this is in place.

**What was measured.** On one rig, an RTX 2060 and a GTX 1650 SUPER (two different chips): windows grown from 256 MB to 8 GB and 4 GB at boot, the integrity test passed twice at 240 cases and 636 GiB of byte-exact copies each time, and exchange benchmarks matching RTX 30 pairs in the same slots. That is the author's rig and one driver version; the write-up says to run the integrity test on your own pair before trusting it.

**Local verdict: no value here. Nothing installed.** Our pair is one Ampere card and one Volta card, not Turing, so the steps do not apply. Cross-generation peer access stays refused: the guide's Volta page needs two V100s and IOMMU passthrough on the stock driver, and the open module cannot load the V100 at all. One detail is worth recording: the 3090 here also reports a 256 MiB window, which means the board's firmware Resizable BAR is not enabled, but by the author's own clarification a bigger window mainly helps traffic between cards rather than single-card inference, and our serving splits layers inside one engine instead of reducing across two. There is nothing to win on the serving path, and changing firmware options would be a host change for no measured gain.

## 11:54pm append — MemT-1.0-Pro and its family: memory as part of the model, not as a cache

One new bookmark from Iris's 11:54pm run: the MemT-1.0-Pro launch from MemTensor and NVIDIA. Nothing was downloaded, built or queued; the notes below are research, and the reason is at the end.

### What it is

[MemT-1.0](https://github.com/MemTensor/MemT-1.0) makes "persistent memory" part of the model's computation instead of a cache you carry beside it. A native memory block runs alongside the backbone's attention: a local memory block holding a multi-channel memory matrix that evolves at every step, plus a hyper memory block with learned query/key/value projections, erase, write and forget gates. During generation the model reads from that memory state and adds the readout to the attention output; at the end of a turn a gated update writes the turn into the state. The state is constant in size, so it does not grow with the history you have already seen.

The [paper](https://arxiv.org/abs/2610.26825) reports a 66x reduction in persistent storage and about 1.86x end-to-end speedup at a 128K-token history, measured on the smallest model. It also reports a 34B-token two-stage training pipeline, and says plainly that its models "remain competitive with retrieval-augmented methods" and "strong textual-memory systems remain ahead overall, particularly on long histories that require detailed evidence retrieval". That is exactly our long-context retrieval row, so the honest reading is: this trades a carried KV cache for a learned summary, with a quality cost on detailed evidence.

Three sizes, all ungated on the Hub, all released 2026-11-21:

- **Nano**, 36B total / 3B active, Qwen3.6-35B-A3B backbone, Apache-2.0, 70.2 GB of bf16 weights.
- **Flash**, 288B / 17B active, DeepSeek-V4-Flash backbone, MIT, 576.0 GB of bf16 weights.
- **Pro**, 554B / 59B active, NVIDIA Nemotron-3-Ultra-550B-A55B backbone, OpenMDW-1.1, 226 shards totalling 1,129,511,817,320 bytes (1.13 TB).

### What we checked

`MemTensor/MemT-1.0-Pro` at `046a1626642f804033cd05330dced47955acdf58` is public and not gated. The 226 shards are about 5 GB each at bf16. The model needs a custom architecture class (`MemTNemotronHForCausalLM`, `trust_remote_code=True`), and on the Nemotron backbone the validated environment adds `mamba-ssm` and `causal-conv1d`. The project's own deployment guide expects SGLang 0.5.16 with a `memt_sglang` package, three source patches, and 8 GPUs at TP8/EP8 for Pro. Flash is specified for 8 GPUs as well; Nano's reference example is 2 GPUs at TP2.

Nobody has published a lower-bit pack of Pro or Flash. A Hub search finds GGUFs only for Nano, from a community uploader, and an EXL3 repo for Nano that contains plots and a demo video but no weights.

### Fit here

Our ceiling is the experts-in-RAM tier: roughly 160 GB of weights across 56 GB of video memory and 125 GB of main memory. Pro is 1.13 TB in bf16, seven times that ceiling. Even a hypothetical 2-bit requant of a 554B model lands near 145 GB of weights and would page through every token from main memory; no such pack exists and we would not be first to make one. **Pro does not fit. Watch it, and nothing else.** Flash is 576 GB at bf16, no quant published, and its reference path wants eight cards, so it does not fit either, although it is at least the same backbone we already serve in its non-memory form.

**Nano is the one that could run.** The community GGUF at [brishen/MemT-1.0-Nano-GGUF](https://huggingface.co/brishen/MemT-1.0-Nano-GGUF) (Apache-2.0) carries Q4_K_M at 21.65 GB and Q8_0 at 37.38 GB, with the memory tensors kept at Q8_0 because their error accumulates over every committed token. Q4_K_M fits fully on the 32 GB card with roughly 10 GiB left for cache and compute, and it is tight but possible on the 24 GB card. Only a handful of layers carry full attention, so a 100K context should fit inside that remainder; that is an estimate from the architecture, not a measurement.

### Engine, and the real catch

Upstream llama.cpp has no MemT support: no issue or pull request in the project carries the name, and the current tensor constants know Nemotron H but no memory tensors. The GGUF therefore needs one commit on top of llama.cpp: [Brishen/llama.cpp, branch `memt-native-memory`](https://github.com/Brishen/llama.cpp/tree/memt-native-memory), commit `e964c415485f3898d2fb4633c79d8ad38b7abdbc`, dated 2026-10-26, exactly one commit ahead of upstream `d854d98b` and touching 30 files. It adds the memory path for CPU and CUDA, the converter, and the server fields `memory_id`, `memory_commit` and `memory_documents` plus `GET /memory` and `POST /memory/{id}?action=save|restore|erase`. States live in main memory by id.

Two things follow from that. First, the base is a month old, so the build has to pin that commit rather than rebase onto today's master, and whether its CUDA memory kernels compile and run for the older card generation is untested, since the fork was written against current cards. Second, and more important: **without `memory_id` the server behaves as the plain backbone.** Our test runner sends ordinary chat completions, one per case row, with no memory id and no commit pass. So a standard viability case here would measure the Qwen3.6-35B-A3B backbone with extra unused weights, not the thing the paper claims.

The measurement that matters needs a small runner extension: one turn that writes a fact with `memory_commit`, a later turn that asks for it under the same `memory_id`, and the same retrieval probe near 100K with and without the memory. Only then is there a number to compare against a normal 100K context.

### Why nothing started

The general queue pause is still in place, the 24 GB card is inside a live test suite right now, and this item needs new lab work (a fork build for both card generations and a memory stage in the runner) rather than an available slot. The archive drive has about 350 GB free, under the 500 GB floor, so nothing goes there; the 21.65 GB pack would fit the temporary overflow disk, but it cannot be served from there without a host change. Nothing downloaded, built, queued or claimed. No case id allocated.

**Next, when the queue opens:** build the fork image for both card generations, pull Q4_K_M to a disk the GPU host can read, add the memory-id and commit path to the runner, then run a viability row plus one memory row and a retrieval probe near 100K. If the fork will not build or run for the older card, that is itself the finding, and Nano can be retried on the newer card alone.
