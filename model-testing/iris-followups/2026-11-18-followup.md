# Iris follow-up, 2026-11-18

## 8am run: Tencent Hy4 flash open weights (backlog: fits on paper, needs a draft llama.cpp PR)

- **What it is:** Tencent has now published the Hy4 flash weights that were API-only on Nov 16
  ([earlier follow-up](2026-11-16-followup.md)). 220B total parameters, of which 64B are the Engram n-gram lookup
  table, 12B active per token, text and image input, up to 1M tokens of context.
  [Iris note](https://github.com/alexderz/agentic-toolbox-misc/blob/main/iris/2026-11-18-steady-alex-bookmarks.md) ·
  [tencent/Hy4-flash](https://huggingface.co/tencent/Hy4-flash) ·
  [AngelSlim GGUFs](https://huggingface.co/AngelSlim/Hy4-flash-GGUF) ·
  [llama.cpp PR #32517](https://github.com/ggml-org/llama.cpp/pull/32517).
- **What we checked (Hugging Face API, read directly):**
  - `tencent/Hy4-flash` @ `d88c9dfd`, ungated: 220.25B parameters in BF16, about 440 GB. `Hy4-flash-FP8` @ `003107fa`
    (about 287 GB) and the pretraining checkpoint `Hy4-flash-base` @ `95b9f823` (219.4B) are also public.
  - Licence: the Tencent Hy License 1.0, which is Apache-2.0 plus commercial terms. A separate licence is needed only
    for a model-as-a-service business over US$50M revenue or 100M monthly users, and internal use is explicitly exempt.
    Unlike some recent custom licences, it has **no territory exclusion**, so it grants us normal use.
  - How it works (from `config.json` and the card): 42 layers (1 dense, 41 MoE). Each token picks 16 of 512 small routed
    experts plus one shared expert, and the experts run in a smaller "latent" width. Attention mixes a 512-token sliding
    window with a DeepSeek-style sparse attention (latent KV, rank 512, with a compressed indexer that picks the top 2048
    positions) at 3 sliding-window layers per sparse layer. That is why the context memory stays small. Engram adds
    hashed bigram and trigram embeddings at layers 2, 12, 22 and 32, stored in FP8. The vision encoder is adapted
    from SigLIP2.
  - GGUFs from Tencent's own compression team (`AngelSlim/Hy4-flash-GGUF` @ `632c8e70`): Q4_K_M 156.8 GiB, Q3_K
    144.7 GiB, IQ2-AH 125.7 GiB, plus two NVIDIA 4-bit float builds aimed at Spark boxes. Every quant ships the
    Engram table as an identical 63.4 GB second shard. The repo's README names an mmproj (vision) file that the repo
    does not contain yet.
  - Engine: stock llama.cpp cannot load it. Support is in PR #32517 (`hy_v4_flash`), which is open, still a draft,
    head `0a054d0b` on Nov 18, and the reviewers have asked the author for another round. SGLang and vLLM recipes are on the card.
- **Local fit on paper (not measured), both GPUs (24 GB + 32 GB) with experts in system RAM:**
  - **Q3_K (about 155 GB on disk): the largest quant that fits.** Roughly 52 GiB of it goes on the cards and about
    93 GiB into RAM, leaving about 20 GiB of RAM for the system and parked sessions.
  - **Q4_K_M (about 168 GB): too tight.** About 105 GiB in RAM leaves too little for parked sessions.
  - **IQ2-AH (about 135 GB): the roomy fallback.**
  - The Engram table only needs a few rows read per token, so it is a natural thing to keep in RAM.
  - With 12B active parameters and the small sparse and sliding-window context memory, this suits our multi-session,
    long-context agent target better than most models of its size, provided the quality holds up.
- **Verdict: backlog (real candidate), deferred because model testing is paused for the port work.** Nothing was
  downloaded, built or queued. There's also no room right now: the storage drive has well under the 155 GB the pull
  needs, so it waits for the new disk anyway. When testing resumes:
  1. Build the PR head for both cards.
  2. Check the GGUF tensor names against that head, since community GGUFs sometimes target a different revision
     than the code that finally merges.
  3. Pull Q3_K.
  4. Run a viability case: fit, tokens per second and time to first token, retrieval near 100K, the quality stage,
     then an agent test. These are text-only rows until our harness has an image stage.

  A cheap hosted OpenRouter run is still on the backlog too.

## 4pm run: AtomicChat's 85 GB Hy4 flash GGUF (backlog: the first build that fits on our two GPUs, blocked on storage)

- **What it is:** a community GGUF of Tencent's Hy4 flash (see the 8am item above) from the team behind the Atomic Chat
  app, aimed at 64 GB machines. It splits the model in two. 49.1 GB covers the network itself: routed experts at about
  2 bits (gate/up IQ2_XXS, down IQ2_S) and everything else at Q8_0. The other 35.6 GB is the Engram table at Q4_0, in a
  file of its own that can stay on disk.
  [Iris note](https://github.com/alexderz/agentic-toolbox-misc/blob/main/iris/2026-11-18-steady-alex-bookmarks.md) ·
  [AtomicChat/Hy4-flash-GGUF](https://huggingface.co/AtomicChat/Hy4-flash-GGUF) ·
  [their metrics](https://huggingface.co/datasets/AtomicChat/Hy4-flash-GGUF-metrics).
- **How the trick works:** Engram is a hashed lookup of learned bigram and trigram embeddings. Each token reads a
  handful of rows (a few KB), so the table behaves like an embedding lookup, not like expert weights that need fast
  memory bandwidth. llama.cpp keeps it on the host with `-ot 'per_layer_token_embd\.weight=CPU'`, and the operating
  system pages in only the rows that get read. Only the 49 GB part has to sit in fast memory.
- **What we checked (Hugging Face API, read directly):**
  - Repo pinned @ `dc1525fe`, not gated. Licence: the Tencent Hy License, inherited from the base model, with no
    territory clause (see the 8am item).
  - The files and sizes match the card: shard 1 49,060,453,184 bytes, shard 2 35,640,346,688 bytes, the vision
    projector 971,849,408 bytes, with sha256 values recorded in our lab notes.
  - The files were built for llama.cpp PR #32517 at `0a054d0b`, the same head as Tencent's AngelSlim files. That is
    still the PR head as of 22:20 UTC on Nov 18, and the PR is still an unmerged draft. The public checkpoint needed a
    small converter patch, which is included in the repo's `conversion/` folder.
- **Their quality numbers (KL divergence against BF16 on their own 30-language corpus; vendor-measured, not ours):**
  - Q8_0: mean KLD 0.136, with 91.8% of tokens getting the same top pick as BF16.
  - Tencent Q4_K_M: 0.198 and 89.3%.
  - Tencent IQ2-AH: 0.651 and 77.9%.
  - This file: 0.725 and 76.4%.

  Even Q8_0 picks a different top token on 8% of tokens. Their reading is that small rounding errors change which 16 of
  the 512 experts the router picks, so this model is unusually sensitive to quantization. They report 23 to 26 tokens/s
  on 4x A100 and have run no task benchmarks. The tool-calling caveat matters for us: with reasoning off, this file
  answered in prose instead of calling the tool, so agent tests should keep reasoning on.
- **Local fit on paper (not measured):**
  - The 49.1 GB part (45.7 GiB) could sit entirely on our two cards (24 + 32 GB), with the Engram table in system RAM.
    That puts it in our fast "fully on GPUs" tier. Hy4 flash's KV cache is small, but 2 to 6 GiB of headroom after the
    floors and compute buffers is tight, so only a real load will tell.
  - This also changes how we read the bigger AngelSlim quants. Their Engram shard is the same 63.4 GB in every quant,
    and that shard can be paged rather than pinned. That makes Q4_K_M (105 GB of network) a plausible experts-in-RAM
    fit after all. The 8am note called it too tight, because it counted the whole table as resident RAM.
  - This is weights read from disk, not saved KV cache, so it stays within our no-disk-KV rule.
- **Verdict: backlog, and worth running.** The interesting test is speed against quality on the same engine build:
  this about-2-bit file fully on the GPUs against Tencent's Q3_K or Q4_K_M with experts in RAM.
- **What is actually blocking it (as of this run):**
  1. **Storage.** Our model storage has about 71 GB free, already under our 500 GB safety floor, and the GPU host's
     local disk has 51 GB. Neither can hold even this 85.7 GB pack. A new disk is on the way.
  2. **GPU time.** A two-card case needs the 24 GB card, which is busy with the current daily-driver test suite. It runs
     in a gap that suite's owner grants.
  3. **Engine.** It needs the draft PR. Building that head takes minutes, so we build it when the download can start,
     because the head may move first.
  Nothing was downloaded, built or queued.
- **Correction to the 8am item:** the reason given there ("paused for the port work") is out of date; that work is
  finished. The real blockers are the three above.
- **Plan once the disk is in:** pull this pack first, because it is smaller and targets the fast tier, then Tencent's
  Q3_K. Build PR #32517 for both cards and check the GGUF tensor names against it. Then run two viability cases (fit,
  tokens/s and time to first token, retrieval near 100K, the quality stage, and an agent test with reasoning on), as
  text-only rows.
