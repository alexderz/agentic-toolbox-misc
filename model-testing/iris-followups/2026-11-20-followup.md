### Maya v1.1.69: Hy4-Flash speed update (engine update)

- **What it is:** the [v1.1.69 release](https://github.com/mw00/project-maya/releases/tag/v1.1.69) of
  [mw00/project-maya](https://github.com/mw00/project-maya) (MIT). Its `maya-hy4` engine runs Tencent's
  [Hy4-flash](https://huggingface.co/tencent/Hy4-flash).
  - Tag `v1.1.69` points at commit `e9cb6510`, published 2026-11-20 09:07 UTC: 71 commits after v1.1.68.
  - Iris linked the alesha-pro fork. That fork's `hy4-flash` branch has not moved since `cbe0a1fe` (the maya-hy4f item on
    11-19), so the release itself is mw00's.
- **What we checked:** the release notes, the diff from v1.1.68, and the engine's options in the source.
  - The llama.cpp pin (`3cf03257`) and the Python requirements are unchanged.
  - New options:
    - `--kv-streaming` / `--kv-resident`: the latent KV cache can sit in pinned host RAM, with only the positions each
      token needs streamed in. In v1.1.68 it was VRAM-only. This is RAM, not disk.
    - `--dfly2`: a small DFly2 drafter, aimed at 8-12 GB cards.
    - `--draft-more` / `--draft-sure` / `--draft-streak`: draft-length controls.
    - `HY4_HOT=1` (opt-in): an adaptive expert cache.
  - `HY4_HOT` saves its scores into the model folder (`<pack>/expert-hot.bin`), so we would leave it off or point it at
    scratch space.
- **Claims that apply to our cards (upstream's numbers, not ours):**
  - Long prompts on NVIDIA: +7-14% on one card, and +28% at 64K / +56% at 128K on three V100s.
  - Multi-GPU decode with drafting: +9-12% (#1056).
  - Longer contexts with the cache in RAM.
  - Upstream credits the long-prompt work to ideas from alesha-pro's Hy4-flash engine, so the two projects are converging.
- **Verdict: relevant, low priority.** Our current Hy4-Flash engine, maya-hy4f on one 3090, already prefills about 1,400
  tok/s at 100K. The previous both-card Maya-L build on v1.1.68 managed about 240 tok/s on a short benchmark, so even
  +56% leaves it well behind on prefill. v1.1.69 is worth measuring for two things:
  - the host-RAM KV path, which could give more context per session;
  - a Hy4 option that uses both cards, since maya-hy4f cannot use the V100.
- **What we started:**
  - Built a v1.1.69 image for both our cards (CUDA 12.9.1, sm_70 + sm_86) on the agent host, with no GPU used. The
    recipe is the v1.1.68 one with only the tag and commit changed.
  - The image (`778e46f94595`, 4.3 GB) passes our no-GPU checks: the engine starts and refuses a missing pack cleanly,
    no library is missing, the server and pack tool start, and a mock server answers.
- **Not run yet:** the A/B against v1.1.68 on both cards, using the same Maya-L weights and config with only the image
  swapped. Both cards are busy with the current agent-test suite, so it waits for a gap. Results will be added here.

### Inkling 2 Mini (Thinking Machines Lab) — TRY; qualified on one card the same night

- **What it is:** [thinkingmachines/Inkling-2-Mini](https://huggingface.co/thinkingmachines/Inkling-2-Mini), Apache-2.0,
  ungated, released 2026-11-20 (revision `ed40e7da`). A natively multimodal sparse MoE: 26.2-26.4B parameters with
  3.4B active, and about 5.4B effective per token because the middle 12 of its 24 layers run three times. 128 experts,
  top 8 per token; hybrid attention with a 1,024-token local window on 18 of 24 layers and full context on the rest;
  1M-token context; text and image in, text out. The base checkpoint is mixed NVFP4/MXFP8 (about 20 GB, so the note's
  "8-bit" is half right: 4-bit experts alongside 8-bit weights).
- **What we checked:** both weight repos with revision pins, the two GGUF layouts that exist for it, the engine state
  upstream, and the vendor benchmark table.
  - GGUF requants: [unsloth/Inkling-2-Mini-GGUF](https://huggingface.co/unsloth/Inkling-2-Mini-GGUF) (`ea0c79b2`,
    UD-IQ1_S 7.76 GB up to UD-Q8_K_XL 22.87 GB, UD-Q4_K_M 16.61 GB) and
    [ggml-org/Inkling-2-Mini-GGUF](https://huggingface.co/ggml-org/Inkling-2-Mini-GGUF) (`db61c5b4`, IQ4_NL 17.63 GB,
    Q8_0 27.82 GB, BF16 52.23 GB).
  - Engine: mainline llama.cpp merged the looped layout on 2026-11-20 (PR #32694, master `29b52d39`). The correctness
    fix PR #32704 is still open, and only Unsloth's NVFP4-preserving `Mainline_Support` files need it; the official
    IQ4_NL decodes the original NVFP4 first and does not. Unsloth's own prebuilt (b12588) serves the root files with
    their DSpark drafter, whose support is still an open PR (#32218).
- **Result, measured on the 24 GB card (one slot, 102,400 context, Q8 KV, 300 W, short qualification, not an
  agent run):**
  - Unsloth UD-Q4_K_XL without drafting: 53 tok/s decode on short prompts, 39 tok/s at a 100K prompt, about 450 tok/s
    prefill, 213-228 s to first token on a 96-100K prompt; 1,690 MiB free at the tightest point (floor 512 MiB).
  - Oracle and retrieval correct: the arithmetic answer and the two codes hidden at about 96K both came back right,
    and the image row at about 100K identified the red square.
  - DSpark drafter arm: not faster in practice — 77 tok/s on a 27-token prompt, but 38.6 tok/s on a 2,048-token
    generation and 36-39 tok/s at 100K, with only 552 MiB free. The no-draft file is the config to use.
  - Official IQ4_NL on mainline b12600: 54 tok/s short, 36 tok/s at 100K, about 290 tok/s prefill, 2,054 MiB free.
  - A smaller ubatch raised prefill to about 490 tok/s but left 414 MiB free, under the memory floor: rejected.
- **Why it matters:** a 26B MoE that sits wholly on one 24 GB card at 100K with room to spare, at 39-53 tok/s. The
  vendor table puts it ahead of a 27B dense on nearly every coding and agentic row (DeepSWE v1.1 48.2% against 42.2%;
  Terminal Bench v2.1 71.6% against 73.0%). Its serving entries are in the catalog and it joins the standing set.
- **Caveats:** the benchmark numbers are the vendor's, not ours. The model card warns of long reasoning loops on hard
  debugging work and recommends capping output tokens and agent turns. The image check above is a one-shot: the lab
  has no graded image stage yet, so graded rows for this model are text-only.
- **What we started:** nothing new beyond what is described here; the engine images, weights and catalog entries were
  built and the qualification above was run by the lab's own bring-up lane. Agent tests are next.

### SSD as the limiting factor for local AI — no action

- **What it is:** a thread on ultra-sparse MoE and storage bandwidth
  ([post](https://x.com/tomgreenwald/status/2123875212093747663)), citing Qwen 3.8 Flash Next at 180B total/6B active,
  GLM 5.3 Flash at 321B/18B and DeepSeek V4.1 Flash at 552B/16B. Commentary, no release.
- **Local verdict: no action.** Our own measurements say prefill is compute-bound on our cards, not storage-bound:
  about 1,400 tok/s on one 24 GB card for a 2-bit Hy4-Flash build, about 240 tok/s for the both-card engine, and
  DeepSeek V4.1 Flash decoded at 10-13 tok/s with a 28 GiB expert cache in RAM. Reading weights from an SSD only
  starts to bind once a model's expert set stops fitting in system memory, and 125 GB of RAM covers everything we
  serve today. A faster drive would not speed up anything we run.
