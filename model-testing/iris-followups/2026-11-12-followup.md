## MACaQ (Huawei Computing Systems Lab quantization toolkit): test the published pack, watch the toolkit

Iris's 4pm run, from [a post by @TeksEdge](https://x.com/TeksEdge/status/2120932135724884318). Model Master's
intake run, Nov 12 afternoon (Central time).

- **What it is:** [huawei-csl/MACaQ](https://github.com/huawei-csl/MACaQ) (Apache-2.0, created Nov 10, about 200
  stars), a post-training quantization toolkit with backends for llama.cpp, vLLM, Diffusers and PyTorch. Paper:
  [arXiv 2611.10649](https://arxiv.org/abs/2611.10649).
- **How it works:** it calibrates each linear layer on its own, with only one layer resident on the GPU at a
  time. That is how it can quantize a 122B model with about 32 GB of GPU memory. Per layer it applies per-channel
  scaling and a block Hadamard rotation, which spreads outliers across a block so that 4-bit codes lose less.
  It then refines the chosen codes with a Hessian-aware search that flips individual FP4 or GGUF codes when that
  lowers the layer's output error on calibration text. It has two products:
  - **Full MACaQ:** new GGUFs (2, 3 and 4 bit) or MXFP4 W4A4 checkpoints for vLLM. These keep the rotation as an
    activation transform, so they need MACaQ's bundled llama.cpp fork (pinned to an upstream commit from late
    August) or its vLLM kernels.
  - **MACaQ-R:** takes an existing Q4_K, Q5_K or Q6_K **MoE** GGUF and rewrites only its weight codes. Block scales,
    tensor types and file size stay the same, so the result loads in **stock llama.cpp** with no new runtime.
- **What we checked:** Huawei published one MACaQ-R pack:
  [huawei-csl/Qwen3.6-35B-A3B-MACaQ-R-GGUF](https://huggingface.co/huawei-csl/Qwen3.6-35B-A3B-MACaQ-R-GGUF)
  (revision `8f8d8fdd`, Apache-2.0, not gated). It has one file, Q4_K_XL, 22,360,455,968 bytes, with no MTP block.
  Its recipe starts from Unsloth's UD-Q4_K_XL at revision `a483e9e6` (the current main), which is 192 bytes
  larger. The vendor's claim is a KL divergence to FP16 of 0.01337 against Unsloth's 0.01573, about 15% lower at
  the same size. The post's community test on Qwen3-4B points the same way (we did not reproduce it).
- **Fit:** 22.4 GB of weights. On the 3090 alone at 96K with an 8-bit K/V cache, our estimate leaves about
  1.1 GiB free, under our 1.5 GiB rule, so both rows run across the 3090 and the V100. The architecture
  (`qwen35moe`) is already served by our llama.cpp build.
- **Started:** both files are downloading, one after the other, with SHA-256 checks: the MACaQ-R pack and,
  as the control, the exact Unsloth file it was refined from. We had Unsloth's UD-Q4_K_M and UD-Q6_K_XL of this
  model, but not the UD-Q4_K_XL parent. Two cases that differ only in the file: `0ky` (Unsloth control) and
  `0kz` (MACaQ-R). Each runs the fit check, oracle, speed benchmark (tokens per second and time to first token),
  quality check and needle retrieval at 30K and 90K. Speed should be identical, since only the codes change.
  Both cases enter the Titan queue as soon as their downloads verify, behind the four-session agent tests
  running now and the ERNIE 5.5 case.
  Our three-task quality check is coarse, so a KL-divergence measurement against a higher-precision copy would
  be the sharper test of the claim. It is noted as the next step if the pair shows no difference.
- **What it would take to make our own:** a refinement needs the original Hugging Face checkpoint, an FP16 GGUF
  "teacher" and roughly 220 GB of working disk for a 35B MoE. It runs on one GPU in a Python 3.12 environment,
  which here would be a container on Titan's V100 (32 GB), plus GPU hours that the queue would have to give up.
  The obvious targets are the MoE quants we actually serve, such as Tiel-Coder 35B-A3B for the four-session
  agent backend. Our Flash-Next daily driver keeps its experts mostly in Q2_K and IQ3 types, which MACaQ-R does not touch. Full MACaQ
  GGUFs would mean adopting a second llama.cpp fork that is two months behind upstream, so that path is a no for
  now. Faster-kernel features need compute capability 9.0 (Hopper), which neither of our cards has.
- **Verdict:** **test** the published pack (queued as above). **Watch** the toolkit, and run our own MACaQ-R
  refinement only if `0kz` shows a measurable quality gain over `0ky`. Nothing installed.
